# מתכנן מטלות עם חיזוי סיכון לאיחור

פרויקט בקורס "וייב קודינג עם קלוד", אוניברסיטת אריאל, סמסטר א' תשפ"ז.
**אבן דרך 2 (M2):** נתונים נקיים ומחברת EDA שבודקת אם יש בהם סיגנל → [`eda.ipynb`](eda.ipynb)

## הבעיה, ולמי היא מיועדת
סטודנטים דוחים מטלות לרגע האחרון ומאחרים בהגשה. אנחנו בונים **מתכנן מטלות לסטודנטים:**
- הסטודנט מזין את המטלות שלו: דדליין, משקל בציון והערכת שעות.
- האפליקציה משבצת את המטלות בלוח שבועי.
- **מודל ML מעריך לכל מטלה את הסיכוי שתוגש באיחור.** לפי הסיכון, הלוח מסמן את המטלה בירוק, בצהוב או באדום, וממליץ מתי להתחיל.

## ה-y
**`is_late`**: האם עבודה כתובה הוגשה **אחרי** יום הדדליין (1) או עד יום הדדליין (0).
- **רק מבין העבודות שהוגשו.** עבודה שלא הוגשה היא בעיקר נשירה מהקורס, וזו תופעה אחרת.
- ב-y יש את שני הסוגים: 80,449 הגשות בזמן (83.2%) ו-16,259 באיחור (16.8%).
- **ה-y חושב מנוסחה:** יום ההגשה פחות הדדליין. לכן עמודות יום ההגשה (`date_submitted`, ‏`days_from_deadline`, ‏`status`) **לא ייכנסו למודל.** אחרת הוא פשוט ילמד את הנוסחה.

## מקור הנתונים
**OULAD, Open University Learning Analytics Dataset.** נתונים **אמיתיים** של האוניברסיטה הפתוחה הבריטית, 2013 עד 2014. לא סינתטיים.
- **הורדה:** [UCI Machine Learning Repository](https://archive.ics.uci.edu/dataset/349/open+university+learning+analytics+dataset)
- **רישיון:** CC BY 4.0. מותר לשנות ולהעלות, עם קרדיט (בסוף העמוד).
- **מה יש:** 7 טבלאות: 7 קורסים, ‏28,785 סטודנטים, מטלות עם דדליין ומשקל, יום ההגשה של כל מטלה, ו-10.6 מיליון רשומות של קליקים באתר הקורס.
- **הקובץ הגדול:** `studentVle.csv` (הקליקים) שוקל 433MB, יותר מהמגבלה של GitHub (100MB). לכן הוא ב-`.gitignore`. בריפו יש:
  - **דגימה** של 1,000 שורות: `data/oulad/studentVle_sample.csv`.
  - **סיכום** שלו: `data/clicks_by_day.csv`.

  את הקובץ המלא מורידים מהקישור של UCI, ושמים ב-`data/oulad/`.

## מה תיקנו ולמה
`clean_oulad.py` מחבר את הטבלאות לטבלה אחת, `data/tma_submissions.csv`: **שורה לכל סטודנט ולכל עבודה כתובה שהוא היה צריך להגיש. ‏124,232 שורות.**

| מה עשינו | שורות | למה |
|---|---|---|
| לקחנו רק עבודות כתובות (TMA) | | במבחנים הממוחשבים (CMA) ‏47% "מאחרים". כנראה הדדליין שם לא מחייב |
| חיברנו כל רישום לקורס עם כל עבודה בקורס | 162,418 | ככה רואים גם עבודות שלא הוגשו |
| הוצאנו מי שביטל את ההרשמה ביום הדדליין או לפניו | ‏36,910- | הוא עזב את הקורס, ולא היה אמור להגיש |
| הוצאנו מי שנרשם אחרי הדדליין | ‏42- | הוא לא יכול היה להגיש |
| הוצאנו ציונים שהועברו מניסיון קודם (`is_banked`) | ‏1,234- | זו לא הגשה אמיתית בסמסטר הזה |
| חישבנו את `is_late` | | אף טבלה לא אומרת אם הוגש באיחור. **הגשה ביום הדדליין עצמו = בזמן**, כי בנתונים אין שעה |
| חישבנו היסטוריה: `prev_status`, ‏`prev_late_rate` | | רק מעבודות **קודמות** באותו קורס, כדי שהמודל יראה רק מה שהיה ידוע לפני הדדליין |
| לא הכנסנו את `final_result` ואת הציון | | **דליפת מידע:** הם ידועים רק אחרי ההגשה |
| סיכמנו את קובץ הקליקים (`summarize_clicks.py`) | 10.6M → 14,310 | 433MB לא עולים ל-GitHub |

**ערכים חסרים, חריגים ושגויים** (הפירוט בסעיף "איכות" במחברת):
| מה | ההחלטה | למה |
|---|---|---|
| `date_submitted`, ‏`days_from_deadline` ו-`is_late` ריקים (22.2%) | **משאירים ריק** | אלה עבודות שלא הוגשו. 0 היה אומר "הוגש ביום הדדליין" |
| `prev_late_rate` ריק (29%) | **משאירים ריק** | אין עבודה קודמת שהוגשה. 0 היה אומר "הגיש הכול בזמן" |
| `imd_band` (מדד העוני של האזור) חסר ב-3.8% | **משאירים ריק** | חוסר אמיתי, אבל העמודה לא נכנסת למודל |
| עבודות במשקל 0% (קורס GGG, והעבודה הראשונה ב-BBB ‏2014J) | **משאירים** | נתון אמיתי. גם באריאל יש מטלות ששוות 0% |
| 69 סטודנטים עם יותר מ-240 קרדיטים | **משאירים** | כנראה טעות במקור, אבל שאר הנתונים בשורות שלהם תקינים |
| הגשות קיצוניות: 167 יותר מחודש לפני הדדליין, 97 באיחור של יותר מחודשיים | **משאירים** | הסטטוס שלהן נכון. בגרפים מציגים טווח מוגבל |
| `imd_band` כתוב "10-20" בלי סימן אחוז | **משאירים** | לא משפיע. בגרפים כותבים "10-20%" |
| כפילויות | **אין** | נבדק במחברת |

## 💡 התובנה
**גילינו שמי שאיחר בעבודה אחת מאחר גם בעבודה הבאה ב-41% מהמקרים, כמעט פי 3 ממי שהגיש אותה בזמן (14%).**
למשתמש זה אומר: איחור אחד הוא סימן אזהרה. אחרי איחור, האפליקציה תסמן את המטלה הבאה בסיכון גבוה ותמליץ להתחיל מוקדם יותר. משתמש חדש, בלי היסטוריה, יישאל: "בסמסטר שעבר, כמה פעמים הגשת באיחור?".

## 🎯 ה-baseline
**"כולם מגישים בזמן" (התשובה הנפוצה): דיוק של 83.2%, אבל 0% זיהוי של מאחרים.**
זה המספר שהמודל ב-M3 צריך לנצח. הנתונים לא מאוזנים, ולכן נמדוד את המודל גם ב-AUC ובכמה מאחרים הוא מזהה, ולא רק בדיוק.

## מה עוד גילינו (מהמחברת)
- **מגישים ברגע האחרון:** בחציון יום לפני הדדליין, ו-29% ביום הדדליין עצמו.
- **אמצע הסמסטר הוא השיא:** 11% איחור בעבודה הראשונה, 22% בשלישית.
- **עומס משפיע רק בקצה:** עד 120 קרדיטים 16% עד 17% איחור, מעל 120 קרדיטים 22%.
- **מי שמגיש בזמן פעיל יותר כל הזמן:** שבועיים לפני הדדליין 37% מהם נכנסים לאתר בכל יום, לעומת 26% מהמאחרים.
- **דליפה:** ‏`days_from_deadline` מתואם עם ה-y ב-0.60, כי ה-y מחושב ממנו. הוא לא ייכנס למודל.

## הקלטים שייכנסו למודל (M3)
רק מה שסטודנט באריאל יכול להזין באפליקציה:
- משקל המטלה.
- מספר המטלה בקורס.
- העומס.
- האם המטלה הקודמת הוגשה באיחור.
- כמה מהמטלות הקודמות הוגשו באיחור.

**לא נכנסים:**
- **קליקים:** אין לנו גישה לקליקים של אריאל.
- **נתונים דמוגרפיים:** הם בריטיים ובעייתיים מבחינת הוגנות.
- **הקורס:** הקורסים הבריטיים לא קיימים באריאל.

## איך מריצים
```
pip install -r requirements.txt
jupyter notebook eda.ipynb
```
ב-Jupyter: **Kernel → Restart & Run All**. כל הנתונים שהמחברת צריכה כבר בריפו.
כדי לבנות את הנתונים מחדש מהמאגר המקורי: `python clean_oulad.py`. אחרי שמורידים את `studentVle.csv` אפשר להריץ גם `python summarize_clicks.py`.
